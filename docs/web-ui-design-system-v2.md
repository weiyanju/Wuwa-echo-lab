# Tethys System - Web UI 设计系统 V2.1

## 1. 文档状态

本文档替代上一版 V2.0 Web UI 方向。

上一版 V2.0 过度偏向完整 IDE 壳设计，包含 Activity Bar、Side Bar、Editor Area、Status Bar、暗色编辑器优先、小圆角和命令面板优先等设定。实践后证明，这套方向对当前 `Wuwa` 工作台过重，容易产生无业务意义的界面栏位、信息挤压和操作路径变长。

当前结论：

- 首页的 `Tethys System / 泰缇斯枢纽` 方向是正确的，应继续保留。
- 登录后的工作台不应被重构成 VS Code 客户端式界面。
- VS Code 官网、Linear、Vercel 的审美可以作为局部参考，但不能直接照搬成完整页面结构。
- 当前圆角版本的工作台基础可以保留，后续应在其上渐进优化。
- 文档目标是约束后续视觉修订，避免再次走向过度 IDE 化。

当前文档关系：

- 根目录 `DESIGN.md` 是当前视觉 token、字体、组件语言和交互状态总入口。
- `docs/product-interface-principles.md` 定义跨端产品行为与数据可信原则。
- 本文定义 Web 长期视觉方向。
- `docs/web-workbench-ui-guidelines.md` 与 `docs/web-homepage-terminal-design.md` 补充页面规则。

这些文档冲突时不能静默以旧文档或现有代码为准，应先确认预期并同步长期规则。

账号、UID、`GameAccount`、API、数据隔离、本地识别、安全和组件 ownership 等非视觉边界，仍遵循既有产品和工程文档。

## 2. 设计北极星

`Wuwa` Web 应该像：

> 一个冷静、精确、圆角化、现代的声骸数据工具。

它不应该像：

- 登录后的营销页。
- VS Code 客户端克隆。
- 黑色开发者控制台。
- 传统企业后台。
- 装饰性 AI Dashboard。

整体气质：

- 清晰。
- 克制。
- 工具型。
- 浅色优先。
- 蓝色强调。
- 圆角但不软萌。
- 高信息密度但不拥挤。
- 长时间使用不会产生视觉疲劳。

## 3. 参考对象的正确用法

### 3.1 可以借鉴什么

从 VS Code 官网借鉴：

- 清晰的顶部导航。
- 明确的产品识别。
- 蓝色作为主操作和选择色。
- 技术产品的可信感。
- 信息表达直接，不依赖花哨装饰。

从 Linear 借鉴：

- 安静的表面。
- 精准的间距。
- 克制但高级的圆角。
- 轻边框和轻阴影纪律。
- 主次内容之间清楚但不刺眼的层级。

从 Vercel 借鉴：

- 极简 chrome。
- 清楚的文字对齐。
- 白色和近白色表面。
- 克制的状态和指标呈现。
- 精确的组件间距。

这些参考是“视觉词汇”，不是“页面骨架”。

### 3.2 不应该借鉴什么

不要照搬：

- VS Code 客户端左侧 Activity Bar。
- VS Code 客户端底部 Status Bar。
- 完整 IDE Shell。
- 用文件标签隐喻普通应用导航。
- 暗色编辑器优先的整体界面。
- 全局命令面板作为主要心智模型。
- Vercel 营销首页式 hero 到登录后工作台。
- Linear 的复杂产品导航，如果它会隐藏 UID / 账号上下文。

## 4. 首页与工作台的边界

### 4.1 首页

首页 / 登录页可以继续保持终端感：

- `Tethys System / 泰缇斯枢纽` 产品识别。
- 浅色终端表面。
- 等宽字体点缀。
- 精确边框。
- 克制动效。
- 登录 / 注册是第一任务。

首页可以比工作台更有氛围，因为它承担产品介绍、建立信任和登录引导。

### 4.2 工作台

登录后的工作台是生产工具，优先级不同：

- 当前 UID / 账号状态清晰。
- 声骸配置效率高。
- 主词条、副词条录入路径短。
- 候选档位和概率易扫读。
- 本地识别复核只在有价值时提高存在感。
- 历史记录能辅助工作，但不覆盖主任务。

工作台应保留当前圆角、浅色、工具型基础，并逐步提升细节质量。除非有单独批准的设计方案，不应再次整体替换成新的应用外壳。

## 5. 布局原则

### 5.1 导航

当前 Web 应继续使用顶部导航：

- 登录后的左侧使用紧凑 `TETHYS` 字标；登录、加载和首次绑定场景可以使用完整 `Tethys System / 泰缇斯枢纽`。
- 中部主要模块入口相对整条导航视觉居中，不受左右控件宽度不对称影响。
- 右侧承载 UID、主题、账号和退出等操作。

不要为当前工作台新增左侧 Activity Bar。

### 5.2 工作台摘要区

可以保留轻量 `hero-band` / terminal summary 形式，但它必须像工作台摘要，而不是营销 hero。

当前基线允许展示：

- 紧凑问候或当前页面上下文。
- 历史声骸数量。
- 总样本数量。
- 当前预测置信度。
- 与上述指标贴近的短时会话增量。

UID 由顶部导航持续展示，摘要区不重复 UID，不展示 API 地址或内部连接状态。

避免：

- 超大营销标题。
- 装饰性全屏背景。
- 大面积渐变。
- 为了视觉留白牺牲数据密度。
- 没有操作意义的状态条。

### 5.3 主工作区

桌面端优先保持实用的两区结构：

- 初始化 / 配置区域，内部内容在可用视口内吸顶并独立管理滚动。
- 当前声骸 / 副词条 / 候选档位区域。

可以使用卡片和面板，但每个面板都必须承担明确任务。不要为了视觉节奏新增无业务意义的面板。

工作台配置行为：0/5 时修改当前空白草稿；已经录入至少一个副词条时，选择不同套装、COST 或主词条立即新建并切换声骸。任何流程变化都必须有专项设计和测试，不能作为普通样式调整隐式发生。

### 5.4 历史记录

历史记录不应主导默认工作台。

推荐方向：

- 默认最小化并位于桌面端右下安全区。
- 可拖动、可折叠或可关闭，并记住有效位置。
- 不默认覆盖候选档位矩阵。
- 不以大卡片堆叠压迫主流程。

### 5.5 识别复核

识别复核是辅助流程，除非存在待处理、冲突或低置信度内容。

默认状态应安静：

- 使用紧凑状态行或小面板。
- 清楚显示数量和刷新入口。
- 没有待处理内容时避免大块空卡。

当存在待确认内容时，复核区可以提高视觉权重。

## 6. 形状、圆角、边框与阴影

上一版 V2.0 中“几乎所有元素强制 0-2px 小圆角”的规则已废弃。

当前圆角方向：

| 元素 | 推荐圆角 |
|---|---:|
| 页面级大容器 / 大面板 | `20px - 24px` |
| 中型卡片 / 指标块 | `14px - 18px` |
| 输入框 / 按钮 / 选择项 | `10px - 14px` |
| badge / pill | 仅语义需要胶囊时使用 `999px` |
| 密集表格或矩阵单元格 | `8px - 12px` |

规则：

- 同一组件族内部圆角应一致。
- 不混用尖锐 IDE 矩形和大圆角卡片。
- 不把圆角当装饰堆满所有元素。
- 当前工作台已有圆角组件可以保留，除非它们造成明确可读性或布局问题。

边框：

- 用 `1px` 浅边框建立结构。
- 浅色模式下优先使用低对比冷灰边框。
- 更强边框只用于 active、focus、selected 等状态。

阴影：

- 默认面板主要依赖边框和背景层级。
- 阴影只用于浮层、弹层或真正需要脱离背景的控件。
- 禁止重阴影、发光边缘和多层装饰阴影。

## 7. 色彩

浅色模式是当前主要设计基准。

核心方向：

- 白色和近白色表面。
- 冷灰页面背景。
- 蓝色主强调。
- 绿色 / 琥珀 / 红色只用于真实状态。
- 不采用大面积紫色或蓝紫色 AI 渐变。

推荐语义方向：

```css
--primary: #0064e0;
--surface-root: #f6f8fb;
--surface-panel: #ffffff;
--surface-soft: #f1f4f7;
--border-soft: #dee3e9;
--border-strong: #ced0d4;
--text-strong: #0a1317;
--text-main: #1c1e21;
--text-muted: #5d6c7b;
```

现有项目 token 可以继续沿用。只有当现有 token 无法表达稳定语义时，才新增 token。

## 8. 字体

Wuwa 的登录后产品界面采用一套克制型 Data Bento 字体系统：学习 AI 数据看板 / Bento 信息图的现代无衬线气质、强数字层级和高密度数据排版，但不复制其配色、页面骨架或装饰性 AI Dashboard 风格。

Web 字体以 `docs/superpowers/specs/2026-07-13-wuwa-typography-system-design.md` 为准：IBM Plex Sans SC 承担中文与常规 UI，IBM Plex Mono 只承担短技术信息；中文、拉丁、数字使用独立语义入口，正式字重为 400 / 500 / 600 / 700。

字体目标：

- 现代无衬线。
- 科技感但中性。
- 中文清晰稳定。
- 数字醒目、有力量、可横向比较。
- 高信息密度但长期使用不疲劳。
- 数据是主角，字体不抢业务流程。

### 8.1 字体 token

前端以 `WuwaFrontend/src/styles/tokens.css` 为字体 token owner：

```css
--font-cjk: "IBM Plex Sans SC", "Noto Sans SC", "Microsoft YaHei UI", system-ui, sans-serif;
--font-ui: var(--font-cjk);
--font-title: var(--font-cjk);
--font-latin: "IBM Plex Sans SC", "IBM Plex Sans", system-ui, sans-serif;
--font-data: var(--font-latin);
--font-mono: "IBM Plex Mono", ui-monospace, Consolas, monospace;
```

使用规则：

- `--font-cjk`：中文 UI 字体入口，由 OFL-1.1 授权的 IBM Plex Sans SC 提供，异常时回退到 Noto Sans SC、Microsoft YaHei UI 与系统字体。
- `--font-ui`：正文、导航、按钮、表单、常规面板标题。
- `--font-title`：页面标题、统计/评估页的大区块标题、登录页产品识别。
- `--font-latin`：TETHYS 品牌、普通拉丁术语和模型名；首版使用 IBM Plex Sans SC 的配套拉丁字形。
- `--font-data`：UID、声骸编号、概率、百分比、样本数、排名、命中率、分数、价格和所有需要横向比较的数字。
- `--font-mono`：仅用于代码、协议、短技术状态和诊断 metadata，不用于大面积正文。

中文字体加载规则：

- IBM Plex Sans SC 只加载 Regular、Medium、SemiBold、Bold 四档 split WOFF2，IBM Plex Mono 只加载 Medium 与 SemiBold。
- 正式 Sans 字重只允许 400 / 500 / 600 / 700；禁止声明 650、680、720、740、760、800、900 等未加载字重。
- 字体文件来自 `@ibm/plex-sans-sc` 与 `@ibm/plex-mono` 官方包，不依赖运行时第三方 CDN。
- active token 只写真实接入的字体和必要系统兜底。没有安装、没有随包提供、也没有被构建引用的字体名不进入代码或规范示例。
- `font-synthesis: none` 必须保留，禁止浏览器伪造粗体或斜体。

### 8.2 字号和字重层级

产品 UI 使用固定字阶；标题字号不随视口连续缩放，窄屏只通过明确媒体查询切换到批准值。

| 角色 | 用途 | 推荐字号 | 推荐字重 | 行高 |
|---|---|---:|---:|---:|
| Page Title | 工作台问候、页面主标题 | 1.75rem / 28px | 700 | 1.15 |
| Section Title | 大区块标题 | 1.3125rem / 21px | 700 | 1.15 |
| Card Title | 卡片、图表、面板标题 | 1rem / 16px | 700 | 1.15–1.25 |
| Body | 正文说明 | 0.9375rem / 15px | 400 | 1.5 |
| Control | 按钮、选项、主要列表文字 | 0.875rem / 14px | 600 | 1.25 |
| Label | 字段、状态、图表类别 | 0.8125rem / 13px | 600 | 1.3 |
| Caption | 说明、来源、辅助 metadata | 0.75rem / 12px | 400–500 | 1.35 |
| Micro | 空间受限的非交互图表 metadata | 0.6875rem / 11px | 500 | 1.35 |
| Data SM | UID、概率、密集表格数字 | 0.9375rem / 15px | 600 | 1.05 |
| Data MD | 普通指标 | 1.125rem / 18px | 600 | 1.05 |
| Data LG | 主指标 | 1.5rem / 24px | 700 | 1.05 |
| Data XL | 页面级分数 | 1.875rem / 30px | 700 | 1.05 |

规则：

- 主标题厚重但克制，最高字重为 700。
- 大数字只在统计、评估、预测摘要、首页状态摘要中放大。
- 工作台录入矩阵、历史记录、识别复核保持紧凑，不使用海报级数字。
- 中文标题和正文使用 `--tracking-cjk: 0`，不做松散字距。
- 英文说明不应比中文标题或数字更抢眼。
- 普通拉丁使用 `--tracking-latin: 0`，缩写使用 `--tracking-abbr: 0.02em`，全大写短状态使用 `--tracking-caps: 0.06em`，TETHYS 品牌使用 `--tracking-brand: 0.08em`。
- 交互文字不得小于 12px；仅空间受限的非交互图表 metadata 可使用 11px。禁止 10px、半像素字号、负字距和裸非零字距。

### 8.3 数字排版规则

所有指标、排名、价格、分数、百分比、概率、样本量、UID、声骸编号和评估分数必须使用稳定数字宽度：

```css
font-family: var(--font-data);
font-variant-numeric: tabular-nums;
font-feature-settings: "tnum";
letter-spacing: var(--tracking-data);
```

全局数字工具类由 `WuwaFrontend/src/styles/base.css` 提供：

```css
.data-number,
.metric-value,
.rank-value,
.score-value,
.percent-value
```

使用规则：

- 数字和单位分层，单位字号约为数字的 55% - 70%。
- 单位字重使用 500 或 600，不能过淡。
- 表格、矩阵和图表轴线中的数字优先稳定宽度，不追求装饰。
- 当前值、对照值和异常值通过既有语义色表达，不引入参考图配色。
- 不使用渐变文字、负字距、过细灰字或装饰字体。

### 8.4 页面应用

- 工作台：保留工具型密度。副词条名、档位和预测概率清晰对齐，数字使用 `--font-data`，不做大指标视觉。
- 统计页：总样本、可靠性、阶段进度、偏离值可以使用 Metric LG / XL 层级。
- 评估页：命中率、Log Loss、Brier Score、模型权重和覆盖范围使用强数字层级。
- 历史记录：只使用稳定数字宽度和紧凑标签，不提高默认视觉权重。
- 识别复核：待处理数量、置信度和状态数字使用 `tabular-nums`，冲突状态通过语义色和文案表达。
- 首页 / 登录页：可以使用更强的 `--font-title`，但不能把登录后工作台变成营销页或 AI 信息图海报。

### 8.5 禁止项

- 不使用手写字体、衬线字体、卡通字体、赛博朋克霓虹字体。
- 不使用渐变文字。
- 不使用负字距。
- 不使用过细灰字承担关键信息。
- 不让英文 caption 压过数字。
- 不为单个页面临时引入新的字体栈。
- 不把参考图的配色或装饰结构带入 Wuwa。

## 9. 组件方向

### 9.1 按钮

- 主按钮使用蓝色实底。
- 次按钮使用浅底或描边。
- 图标按钮仅用于明确工具动作。
- hover 不应上浮或缩放。
- disabled、loading、saving 状态必须明确。

### 9.2 卡片和面板

- 卡片用于真实分组，不用于装饰堆叠。
- 不要卡片套卡片。
- 面板标题、说明和内容之间保持稳定间距。
- 重要数据靠近相关操作。

### 9.3 表格和矩阵

- 表格 / 矩阵优先保证对齐、稳定行高和数值可比性。
- 长文本可以截断，但不能挤压操作区。
- 状态 badge 不应造成行高跳动。
- 预测值、概率、置信度的格式必须一致。

### 9.4 表单和选择项

- 录入顺序必须符合用户实际操作流。
- 当前选择状态要明显。
- 候选项不应因 hover 或选中造成布局移动。
- 错误文案就近显示，并说明下一步。

## 10. 动效与反馈

动效应短、稳、少。

允许：

- 背景色变化。
- 边框色变化。
- 透明度变化。
- 轻微且不影响布局的浮层出现。

避免：

- hover 上浮。
- hover 缩放。
- 弹性动画。
- bounce / spring。
- 因动画造成文字或按钮重排。

建议过渡时间：

- 常规 hover：`80ms - 120ms`。
- 面板显隐：`120ms - 160ms`。
- 用户输入反馈：尽量即时。

必须尊重 `prefers-reduced-motion`。

## 11. 当前基线与演进方式

当前 Web 已形成以下基线：

1. IBM Plex 字体系统、稳定数字宽度和真实字重。
2. 紧凑 `TETHYS` 顶部导航与视觉居中的主导航。
3. 历史声骸、总样本和置信度组成的紧凑摘要区。
4. 带搜索和视口内吸顶内容的初始化配置区。
5. 清楚的档位保存、已录入和预测状态。
6. 默认最小化在右下安全区的浮动历史面板。
7. 浅色优先、暗色等价映射和明确响应式断点。

后续工作台 UI 仍应渐进演进，不一次性替换应用外壳。新改动必须解决明确任务问题，并把已经成为长期事实的变化同步回本文件、`DESIGN.md` 和对应页面规范。

纯视觉改动必须保持：

- Vue 组件职责不变。
- 业务语义不变；若流程需要改变，先批准专项设计并补充状态与回归测试。
- API 契约不变。
- 账号 / UID 心智不变。
- feature CSS ownership 不变。

## 12. 明确禁止项

在新的方案被单独批准前，不要添加：

- 左侧 Activity Bar。
- 底部全局 Status Bar。

## 13. 后续 UI 改动验收标准

一次工作台 UI 改动只有在满足以下条件时才应被接受：

- 保留首页终端风方向。
- 改善一个明确的工作台流程。
- 保留当前圆角基础，或只做有理由的细节优化。
- 对 VS Code 官网 / Linear / Vercel 的借鉴是局部的，不是照搬。
- 减少视觉噪音，而不是增加界面 chrome。
- 桌面端可读、稳定、无明显错位。
- 不破坏测试、构建或组件边界。
- 配置变化、保存中、已录入、预测和历史面板状态与当前长期规则一致。
- 大改动提交前应提供截图或浏览器检查结果。
