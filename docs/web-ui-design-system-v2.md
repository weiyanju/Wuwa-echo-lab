# Wuwa Echo Terminal - Web UI 设计系统 V2.1

## 1. 文档状态

本文档替代上一版 V2.0 Web UI 方向。

上一版 V2.0 过度偏向完整 IDE 壳设计，包含 Activity Bar、Side Bar、Editor Area、Status Bar、暗色编辑器优先、小圆角和命令面板优先等设定。实践后证明，这套方向对当前 `Wuwa` 工作台过重，容易产生无业务意义的界面栏位、信息挤压和操作路径变长。

当前结论：

- 首页的 `Wuwa Echo Terminal / 鸣潮声骸终端` 方向是正确的，应继续保留。
- 登录后的工作台不应被重构成 VS Code 客户端式界面。
- VS Code 官网、Linear、Vercel 的审美可以作为局部参考，但不能直接照搬成完整页面结构。
- 当前圆角版本的工作台基础可以保留，后续应在其上渐进优化。
- 文档目标是约束后续视觉修订，避免再次走向过度 IDE 化。

当本文档与以下文档中的旧描述冲突时，以本文档为准：

- `docs/product-interface-principles.md`
- `docs/web-workbench-ui-guidelines.md`
- `docs/web-homepage-terminal-design.md`

账号、UID、`GameAccount`、API、数据隔离、本地识别、安全和组件 ownership 等非视觉边界，仍遵循既有产品和工程文档。

## 2. 设计北极星

`Wuwa` Web 应该像：

> 一个冷静、精确、圆角化、现代的声骸数据工具。

它不应该像：

- 登录后的营销页。
- VS Code 客户端克隆。
- 黑色开发者控制台。
- 传统企业后台。
- 装饰性 AI Dashboard。

整体气质：

- 清晰。
- 克制。
- 工具型。
- 浅色优先。
- 蓝色强调。
- 圆角但不软萌。
- 高信息密度但不拥挤。
- 长时间使用不会产生视觉疲劳。

## 3. 参考对象的正确用法

### 3.1 可以借鉴什么

从 VS Code 官网借鉴：

- 清晰的顶部导航。
- 明确的产品识别。
- 蓝色作为主操作和选择色。
- 技术产品的可信感。
- 信息表达直接，不依赖花哨装饰。

从 Linear 借鉴：

- 安静的表面。
- 精准的间距。
- 克制但高级的圆角。
- 轻边框和轻阴影纪律。
- 主次内容之间清楚但不刺眼的层级。

从 Vercel 借鉴：

- 极简 chrome。
- 清楚的文字对齐。
- 白色和近白色表面。
- 克制的状态和指标呈现。
- 精确的组件间距。

这些参考是“视觉词汇”，不是“页面骨架”。

### 3.2 不应该借鉴什么

不要照搬：

- VS Code 客户端左侧 Activity Bar。
- VS Code 客户端底部 Status Bar。
- 完整 IDE Shell。
- 用文件标签隐喻普通应用导航。
- 暗色编辑器优先的整体界面。
- 全局命令面板作为主要心智模型。
- Vercel 营销首页式 hero 到登录后工作台。
- Linear 的复杂产品导航，如果它会隐藏 UID / 账号上下文。

## 4. 首页与工作台的边界

### 4.1 首页

首页 / 登录页可以继续保持终端感：

- `Wuwa Echo Terminal` 产品识别。
- 浅色终端表面。
- 等宽字体点缀。
- 精确边框。
- 克制动效。
- 登录 / 注册是第一任务。

首页可以比工作台更有氛围，因为它承担产品介绍、建立信任和登录引导。

### 4.2 工作台

登录后的工作台是生产工具，优先级不同：

- 当前 UID / 账号状态清晰。
- 声骸配置效率高。
- 主词条、副词条录入路径短。
- 候选档位和概率易扫读。
- 本地识别复核只在有价值时提高存在感。
- 历史记录能辅助工作，但不覆盖主任务。

工作台应保留当前圆角、浅色、工具型基础，并逐步提升细节质量。除非有单独批准的设计方案，不应再次整体替换成新的应用外壳。

## 5. 布局原则

### 5.1 导航

当前 Web 应继续使用顶部导航：

- 左侧展示产品名或品牌。
- 中部或左中部展示主要模块入口。
- 右侧承载 UID、主题、账号和退出等操作。

不要为当前工作台新增左侧 Activity Bar。

### 5.2 工作台摘要区

可以保留轻量 `hero-band` / terminal summary 形式，但它必须像工作台摘要，而不是营销 hero。

允许展示：

- 当前模块标题。
- UID / API 状态。
- 历史记录数量。
- 样本数量。
- 置信度 / 识别状态。
- 简短上下文文案。

避免：

- 超大营销标题。
- 装饰性全屏背景。
- 大面积渐变。
- 为了视觉留白牺牲数据密度。
- 没有操作意义的状态条。

### 5.3 主工作区

桌面端优先保持实用的两区结构：

- 初始化 / 配置区域。
- 当前声骸 / 副词条 / 候选档位区域。

可以使用卡片和面板，但每个面板都必须承担明确任务。不要为了视觉节奏新增无业务意义的面板。

### 5.4 历史记录

历史记录不应主导默认工作台。

推荐方向：

- 默认轻量。
- 可折叠或可关闭。
- 后续可探索右侧 dock。
- 不默认覆盖候选档位矩阵。
- 不以大卡片堆叠压迫主流程。

### 5.5 识别复核

识别复核是辅助流程，除非存在待处理、冲突或低置信度内容。

默认状态应安静：

- 使用紧凑状态行或小面板。
- 清楚显示数量和刷新入口。
- 没有待处理内容时避免大块空卡。

当存在待确认内容时，复核区可以提高视觉权重。

## 6. 形状、圆角、边框与阴影

上一版 V2.0 中“几乎所有元素强制 0-2px 小圆角”的规则已废弃。

当前圆角方向：

| 元素 | 推荐圆角 |
|---|---:|
| 页面级大容器 / 大面板 | `20px - 24px` |
| 中型卡片 / 指标块 | `14px - 18px` |
| 输入框 / 按钮 / 选择项 | `10px - 14px` |
| badge / pill | 仅语义需要胶囊时使用 `999px` |
| 密集表格或矩阵单元格 | `8px - 12px` |

规则：

- 同一组件族内部圆角应一致。
- 不混用尖锐 IDE 矩形和大圆角卡片。
- 不把圆角当装饰堆满所有元素。
- 当前工作台已有圆角组件可以保留，除非它们造成明确可读性或布局问题。

边框：

- 用 `1px` 浅边框建立结构。
- 浅色模式下优先使用低对比冷灰边框。
- 更强边框只用于 active、focus、selected 等状态。

阴影：

- 默认面板主要依赖边框和背景层级。
- 阴影只用于浮层、弹层或真正需要脱离背景的控件。
- 禁止重阴影、发光边缘和多层装饰阴影。

## 7. 色彩

浅色模式是当前主要设计基准。

核心方向：

- 白色和近白色表面。
- 冷灰页面背景。
- 蓝色主强调。
- 绿色 / 琥珀 / 红色只用于真实状态。
- 不采用大面积紫色或蓝紫色 AI 渐变。

推荐语义方向：

```css
--primary: #0064e0;
--surface-root: #f6f8fb;
--surface-panel: #ffffff;
--surface-soft: #f1f4f7;
--border-soft: #dee3e9;
--border-strong: #ced0d4;
--text-strong: #0a1317;
--text-main: #1c1e21;
--text-muted: #5d6c7b;
```

现有项目 token 可以继续沿用。只有当现有 token 无法表达稳定语义时，才新增 token。

## 8. 字体

主字体使用系统 sans-serif，优先保证中文清晰可读。

工作台、统计、评估三个登录后核心 tab 必须共享同一套产品字体体系，参考 VS Code 官网的清晰产品感，而不是复制其营销页大标题：

- UI 主字体：中文优先使用 `"Microsoft YaHei UI", "Microsoft YaHei"`，完整栈为 `"Microsoft YaHei UI", "Microsoft YaHei", "Segoe UI", "Noto Sans SC", system-ui, sans-serif`。它应承担正文、导航、按钮、表单、面板标题和大多数中文内容。
- 标题字体：仍使用 UI 主字体，只通过字号、字重和空间建立层级。工作台内不使用衬线字体、书法感字体或装饰 display font。
- 数值字体：UID、声骸编号、百分比、概率、样本数、版本/状态码使用 `ui-monospace, "SF Mono", Consolas, "Liberation Mono", monospace` 或启用 `tabular-nums`，保证横向比较稳定。
- 标签字体：小标签、状态、导航、badge 使用 0.75rem - 0.875rem，字重 600 - 700，可轻微增加正字距；不要用 800/900 制造噪音。
- 正文字体：说明文案使用 0.875rem - 1rem，字重 400 - 500，颜色通过语义层级区分，不依赖过粗字重。

等宽字体只能作为点缀：

- 协议标签。
- UID。
- 技术状态。
- 数值。
- 短 metadata。

不要把整个工作台强行变成代码编辑器视觉。

字号原则：

- 页面和区域标题清楚但不 hero 化。
- 面板标题紧凑。
- 表格、矩阵和数值优先服务扫读。
- 中文 UI 不使用负字距。
- 登录后产品 UI 使用固定 rem 字阶，不使用随视口宽度变化的 `clamp()` 作为常规标题字号；`clamp()` 仅允许在首页/登录页这类展示性页面使用。
- 数字需要横向比对时必须使用 `font-variant-numeric: tabular-nums`。
- 同一语义角色在三个 tab 中保持同样字重：标题 650 - 700，操作按钮 650 - 700，正文 400 - 500，辅助说明 400 - 500，数据强调 650 - 750。

## 9. 组件方向

### 9.1 按钮

- 主按钮使用蓝色实底。
- 次按钮使用浅底或描边。
- 图标按钮仅用于明确工具动作。
- hover 不应上浮或缩放。
- disabled、loading、saving 状态必须明确。

### 9.2 卡片和面板

- 卡片用于真实分组，不用于装饰堆叠。
- 不要卡片套卡片。
- 面板标题、说明和内容之间保持稳定间距。
- 重要数据靠近相关操作。

### 9.3 表格和矩阵

- 表格 / 矩阵优先保证对齐、稳定行高和数值可比性。
- 长文本可以截断，但不能挤压操作区。
- 状态 badge 不应造成行高跳动。
- 预测值、概率、置信度的格式必须一致。

### 9.4 表单和选择项

- 录入顺序必须符合用户实际操作流。
- 当前选择状态要明显。
- 候选项不应因 hover 或选中造成布局移动。
- 错误文案就近显示，并说明下一步。

## 10. 动效与反馈

动效应短、稳、少。

允许：

- 背景色变化。
- 边框色变化。
- 透明度变化。
- 轻微且不影响布局的浮层出现。

避免：

- hover 上浮。
- hover 缩放。
- 弹性动画。
- bounce / spring。
- 因动画造成文字或按钮重排。

建议过渡时间：

- 常规 hover：`80ms - 120ms`。
- 面板显隐：`120ms - 160ms`。
- 用户输入反馈：尽量即时。

必须尊重 `prefers-reduced-motion`。

## 11. 渐进优化路线

后续工作台 UI 不应一次性大重构。推荐顺序：

1. 统一圆角、边框、背景和阴影 token。
2. 优化顶部导航和工作台摘要区。
3. 改善初始化配置区的可读性和点击效率。
4. 优化当前声骸、副词条和候选档位矩阵。
5. 降低识别复核默认干扰。
6. 调整历史记录与主工作区的关系。
7. 做暗色模式一致性。
8. 桌面方案确认后再系统处理移动端。

每一步都必须保持：

- Vue 组件职责不变。
- 业务逻辑不变。
- API 契约不变。
- 账号 / UID 心智不变。
- feature CSS ownership 不变。

## 12. 明确禁止项

在新的方案被单独批准前，不要添加：

- 左侧 Activity Bar。
- 底部全局 Status Bar。
- 完整 IDE Shell 网格。
- 暗色编辑器优先 UI。
- 用于 `工作台 / 统计 / 评估` 的文件标签隐喻。
- 全局命令面板主导的 UX。
- 登录后的大 hero 装饰区。
- 新 UI 框架。
- 新全局状态管理。

## 13. 后续 UI 改动验收标准

一次工作台 UI 改动只有在满足以下条件时才应被接受：

- 保留首页终端风方向。
- 改善一个明确的工作台流程。
- 保留当前圆角基础，或只做有理由的细节优化。
- 对 VS Code 官网 / Linear / Vercel 的借鉴是局部的，不是照搬。
- 减少视觉噪音，而不是增加界面 chrome。
- 桌面端可读、稳定、无明显错位。
- 不破坏测试、构建或组件边界。
- 大改动提交前应提供截图或浏览器检查结果。
