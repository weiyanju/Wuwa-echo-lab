# 历史资料归档说明

`docs/archive/` 用于保存已经完成阶段使命的历史资料，以及每个独立功能、阶段或重构单元完成后的实施与验收记录。

归档资料可以包括：

- 已完成 milestone 的执行计划
- 旧方案设计
- 阶段性调研记录
- 已被长期规范吸收的临时说明
- 不再作为当前默认入口的历史 prompt 或 spec
- 已完成功能的实际实施记录
- 重构结果、验证证据和计划偏差说明

规则：

- 顶层 `docs/` 只保留当前有效的长期规范。
- 新增长期规则应写入顶层对应规范文档。
- 新增阶段性或历史性资料应优先放入 `docs/archive/`。
- 归档资料不能覆盖顶层长期规范。
- 如果归档资料与顶层长期规范冲突，以顶层长期规范为准。
- 每个可以独立验收的功能、阶段或重构单元完成后，应新增一份归档记录。
- 归档记录只描述实际结果，不复制整套长期规范。
- 新功能开始前，应先阅读顶层总规范，再阅读对应专项文档和相关归档决策。

当前 `docs/superpowers/plans/` 和 `docs/superpowers/specs/` 仍保留为既有阶段资料位置。后续整理历史资料时，应逐步迁移或索引到 `docs/archive/`。

## 文件命名

统一使用：

```text
YYYY-MM-DD-<阶段或功能>-implementation.md
```

示例：

```text
2026-06-18-milestone-8-2-settings-diagnostics-implementation.md
2026-06-18-web-component-refactor-implementation.md
2026-06-18-backend-service-refactor-implementation.md
```

同一天同一功能需要继续补充时，优先更新原文档，不重复创建内容高度相似的文件。

## 归档记录模板

```markdown
# <功能或阶段名称>实施记录

## 目标

## 实际完成内容

## 修改模块与文件

## API、数据库与数据边界变化

## 性能与资源影响

## 测试与验收结果

## 与原计划的偏差

## 遗留问题

## 长期规范同步

## 下一阶段入口
```

填写规则：

- 没有发生的 API、数据库、性能或规范变化应明确写“无”，不能省略造成歧义。
- 测试结果必须写实际执行的命令或验证范围，不能只写“测试通过”。
- 与原计划有偏差时要说明原因和影响。
- “长期规范同步”应列出更新过的顶层文档；如果不需要同步，应说明本次仅实现既有规则。
- “下一阶段入口”只记录已经确认的下一步，不把未确认设想写成承诺。
