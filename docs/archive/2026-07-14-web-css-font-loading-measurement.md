# Web CSS 与字体加载实测记录

## 目的

Impeccable 审查曾根据生产构建目录中的文件数量，提出“单一 CSS 过大”和“874 个拆分 WOFF2 约 23 MB”的风险。本次按项目设计治理规则先测量真实页面请求，再决定是否修改加载方式；不把构建产物总量直接等同于首屏下载量。

## 测量条件

- 以当前 Vite 生产构建为对象。
- 使用本地静态服务器加载生产登录页，通过服务器访问日志记录浏览器实际请求集合。
- 浏览器请求为缓存复验的 `304`，冷加载等价体积按对应构建文件大小计算。
- 当前应用是单页应用，`main.js` 全局导入 `style.css`；登录页、UID 绑定页和主应用共享同一份 CSS，不会在页面状态切换时重复下载。

## 构建数据

- 主 CSS：829,905 bytes，Vite 报告 gzip 237.66 kB。
- 主 JavaScript：238.33 kB，Vite 报告 gzip 74.56 kB。
- 字体声明源 CSS：716,212 bytes。
- 项目样式源 CSS：247,489 bytes，其中 feature 样式为 212,877 bytes。
- feature 样式逐文件 gzip 估算合计约 35.15 kB；排除登录页自身样式后，页面级拆分对登录首屏的理论上限约 32.32 kB，实际经合并压缩后的收益只会更小。

## 登录页真实字体请求

登录页实际请求 31 个唯一 WOFF2 子集，冷加载等价体积合计 1,176,408 bytes：

- Regular：8 个，313,724 bytes。
- Medium：6 个，209,360 bytes。
- SemiBold：9 个，334,956 bytes。
- Bold：8 个，318,368 bytes。

其中包含 IBM Plex Mono 的 Medium 与 SemiBold Latin1 子集。这个结果证明构建目录中的 874 个字体文件不会在首屏全部下载；浏览器依据 `unicode-range` 和实际文字只请求需要的子集。

## 方案判断

### 不改用完整字体文件

四个当前使用的 IBM Plex Sans SC 完整 WOFF2 合计约 15.69 MB，明显高于登录页实际请求的约 1.18 MB。用四个大文件换取更少请求会增加首屏传输，不采用。

### 当前不拆分页面 CSS

要真正按页面拆分 feature CSS，需要同时调整 `App.vue` 的静态组件导入和样式 ownership，引入异步组件加载边界。登录首屏的理论 gzip 收益仅约 32.32 kB，而字体声明仍需保留；在本地开发阶段，这个收益不足以覆盖新增复杂度、样式到达时序和潜在闪烁风险，因此本阶段不修改代码。

### UID 绑定页与主应用

两者与登录页共享已加载的全局 CSS。单页状态切换不会再次传输主 CSS 或已缓存字体，只会在出现新字符时按需请求额外的 Unicode 子集。因此没有依据把三个页面拆成三套字体或视觉体系。

## 结论与后续门槛

- 本阶段完成测量，不实施为了审计分数而进行的 CSS 或字体改造。
- 生产部署时应为带内容哈希的 CSS、JavaScript 和字体资源配置长期不可变缓存，并启用 gzip 或 Brotli；这属于服务器部署配置，不在当前本地开发阶段提前假设。
- 只有真实部署环境的冷启动数据证明样式或字体成为主要瓶颈时，才重新评估组件级代码分割或项目字符子集方案。
- 后续方案必须保留现有 IBM Plex 字体角色、四档字重和当前视觉基线，并同时验证缺字回退与动态内容。
