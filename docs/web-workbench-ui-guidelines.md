# Web 工作台 UI 规范

本文件用于约束登录后“工作台”页面的设计和实现。根目录 `DESIGN.md` 定义当前视觉 token、字体和组件语言，`docs/web-ui-design-system-v2.md` 定义 Web 长期方向，本文补充工作台页面规则。三者冲突时不能静默选边，应先确认预期并同步长期文档。

## 当前结论

工作台不再采用完整 IDE 化重构方案。

上一版方案中过度借鉴了 VS Code 客户端的 Activity Bar、Status Bar、强分栏和工具壳结构，导致页面出现了不必要的左侧窄栏、底部状态条、信息挤压和语义不清的问题。这些元素已经不再作为工作台目标方向。

当前工作台应回到原有圆角版本的基础上做渐进式优化：保留工具型产品的效率和信息密度，同时通过更好的圆角、边框、间距、层级、状态反馈和局部导航处理，让页面更接近现代生产力工具的质感。

## 可借鉴对象

VS Code 官网、Linear 和 Vercel 可以作为视觉气质参考，但只能局部吸收，不能直接照搬为完整结构。

- VS Code 官网：借鉴清晰的产品识别、干净的顶部导航、蓝色主操作、理性的技术产品气质。
- Linear：借鉴克制的圆角、轻量边框、安静表面、清晰任务层级和长期使用的舒适度。
- Vercel：借鉴简洁留白、文本对齐、白色空间控制和少装饰的高级感。

这些参考是视觉语言，不是页面骨架。工作台不是 VS Code 客户端，也不是营销首页。

## 不再采用

以下方向不应继续用于当前工作台：

- 左侧 Activity Bar。
- 底部 Status Bar。
- 文件标签式页面切换。
- 全 IDE 式三栏外壳。
- 深色编辑器优先的视觉体系。
- 大面积紫色、蓝紫色 AI 风格。
- 大 hero、营销卡片、装饰渐变。
- 为了“像 VS Code”而添加无明确业务价值的栏位。

## 设计目标

工作台应像一个高效的声骸分析和录入工具：

- 第一眼能理解当前处于哪个 UID、哪个工作状态。
- 录入套装、COST、主词条、副词条和候选档位时路径短、反馈明确。
- 概率、置信度、待处理、已记录、保存中、错误等状态容易扫读。
- 历史记录能辅助工作，但不压迫主流程。
- 本地识别复核在需要时出现，不需要时保持安静。
- 桌面端优先保证信息密度和稳定布局。
- 移动端当前不是主要重构目标，但不能出现明显横向溢出或控件重叠。

## 页面结构

### 顶部导航

顶部导航保留为主要全局导航，不新增左侧窄栏。

要求：

- 左侧使用紧凑 `TETHYS` 字标，完整 `Tethys System / 泰缇斯枢纽` 留在登录、加载和首次绑定等入口场景。
- “工作台 / 统计 / 评估”相对整条顶部导航视觉居中，不能因为左右控件宽度不对称而偏移。
- 当前模块和关键操作清晰。
- 导航高度克制，不占用过多垂直空间。
- 主操作使用蓝色强调，次级操作使用浅色或描边。
- 不把“工作台 / 统计 / 评估”等主导航压缩成竖排图标栏。

### 工作台摘要区

摘要区可以保留轻量终端感，但不能变成营销 hero。

当前基线：

- UID 由顶部导航持续展示，摘要区不重复 UID，也不暴露 API 地址或内部连接细节。
- 摘要区使用紧凑问候语，以及“历史声骸 / 总样本 / 置信度”三项可比较指标。
- 本次新增声骸和样本可以使用贴近指标的短时增量反馈，但不能增加长期占位的装饰状态条。
- 零样本时摘要保持“历史声骸 0 / 总样本 0 / 置信度 --”；置信度不得显示“未建立”、`低` 或 `0%`。
- 信息横向排列、清楚分组，摘要高度保持克制，让工作区尽早进入首屏。

### 初始化与配置区

配置区是工作台的起点，必须比装饰更重要。

要求：

- 套装、COST、主词条的配置顺序清楚，副词条档位录入属于右侧矩阵。
- 套装列表提供搜索，搜索只过滤可见项，不改变当前已选套装。
- 高频选项应该易点、易扫读。
- 当前选择状态要明显，但不使用过重阴影或大面积填色。
- 可以使用圆角卡片或分组面板，但不能层层套卡。
- 当前声骸为 0/5 时，配置变化直接修改空白草稿；已有至少一个副词条时，选择不同配置立即新建并切换到对应声骸。
- 会新建声骸时提前显示“选择其他配置将新建声骸”，创建成功后使用就地状态反馈。
- 总样本为 0 时，在初始化说明位置显示一条紧凑首次录入指引；工作台保持直接可操作，不增加阻塞弹窗、额外开始按钮或模拟数据。
- 桌面端左侧外层参与主网格，内部配置内容在可用视口内吸顶并独立滚动，不被右侧矩阵总高度无限拉长。

### 活跃声骸与候选档位区

这是工作台的核心区域。

要求：

- 当前声骸、主词条、副词条、候选档位和概率应建立稳定视觉层级。
- 表格或矩阵类区域优先保证对齐和扫读，不追求装饰。
- 数值、概率和置信度应使用一致格式和稳定宽度。
- 禁用、待选、已选、错误、保存中状态必须可区分。
- 保存一个档位时暂时锁定整个矩阵，并明确标记正在保存的目标；已录入行只强化实际档位。
- 预测摘要使用“预测 / 其他可能”，显示概率相同的并列预测，避免把模型输出写成替用户作出的“建议”。

### 本地识别复核区

复核区应降低默认干扰，只在需要用户处理时提高存在感。

要求：

- 没有待处理内容时保持轻量。
- 有冲突、低置信度或待确认内容时再强化提示。
- 不抢占配置和录入主流程。
- 操作按钮语义清楚，避免过多同权重按钮并列。
- 当前声骸右侧栏使用弹性居中的预测区与底部单行操作坞；预测和操作共享左右边界，撤销与弃置使用同规格纯图标辅助按钮，“下一个”使用文字主按钮，窄屏时整栏移到记录区下方而不压缩操作坞。

### 历史记录区

历史记录是辅助面板，不应压迫主操作区。

要求：

- 桌面端使用可拖动、可收起的浮动面板；没有保存位置时默认以最小化状态出现在右下安全区。
- 无可见历史且没有保存过最小化偏好时默认最小化；已经保存的展开或最小化偏好优先。
- 默认位置、宽度和层级不能遮挡主录入与关键操作。
- 当前记录、最近记录、筛选和恢复动作要清晰。
- 历史筛选使用互斥胶囊；选中项通过完整语义色填充和数量徽标反色表达，不使用勾选图标或预留图标空位，切换时不得改变控件尺寸与换行位置。
- 避免过重卡片堆叠。

## 视觉规范

### 圆角

圆角是当前版本可以局部吸收 Linear / Vercel 气质的重点。

- 页面级大容器：`20px - 24px`。
- 中型面板和卡片：`14px - 18px`。
- 输入框、选择项、按钮：`10px - 14px`。
- badge / pill：仅在语义上需要胶囊形时使用 `999px`。
- 密集矩阵单元格：`8px - 12px`。

避免全局统一小圆角，也避免所有元素都变成胶囊。

### 边框与阴影

- 以 `1px` 浅边框建立结构。
- 阴影只用于浮层、弹层或真正需要脱离背景的面板。
- 不使用大面积玻璃拟态、重阴影或发光边缘。
- hover 可以改变边框、背景或文字色，不应造成布局跳动。

### 色彩

- 浅色模式是优先设计对象。
- 蓝色作为主操作和关键状态色。
- 中性色用于文字层级、边框、背景和辅助信息。
- 成功、警告、错误只用于真实状态，不用于装饰。
- 暗色模式如存在，应在浅色稳定后做等价适配。

### 字体

- 中文与常规 UI 使用 `IBM Plex Sans SC`，回退到 `Noto Sans SC`、`Microsoft YaHei UI` 和系统字体；技术短文本使用 `IBM Plex Mono`。
- 中文、普通拉丁、品牌、数据和技术 Mono 分别通过 `--font-cjk`、`--font-latin`、`--font-data`、`--font-mono` 进入样式。
- 等宽字体只用于状态码、协议和短技术 metadata；UID、概率、样本量等可比较数字使用 `--font-data` 与 `tabular-nums`，不默认改成 Mono。
- 工作台正文不应大面积使用等宽字体。
- 标题和控件文本保持紧凑，避免首页式大字号。
- 工作台、统计、评估三个 tab 共享同一套字体角色：导航/标题/正文/标签/数据分别使用稳定语义 token，不为单个页面临时引入新的字体风格。
- 工作台问候语、区域标题和面板标题都使用产品 UI sans-serif，不使用衬线或装饰字体；个性通过留白、边框、颜色和轻量图形表达。
- 声骸编号、UID、概率、样本数和评估分数必须使用等宽数字或 `tabular-nums`，保证纵向列表和矩阵扫读稳定。
- 副词条矩阵不需要额外表头解释“副词条 / 候选档位 / 出现概率”；矩阵内容本身应通过左侧词条名、右侧候选值和下方概率自然表达。
- Sans 只使用已经加载的 400 / 500 / 600 / 700，Mono 只使用 500 / 600；禁止 750、800、900 和其他未加载或合成字重。
- 中文默认字距为 0；品牌、缩写和全大写短状态只使用命名 tracking token，不写裸字距或负字距。

## 交互状态

所有高频操作都必须有稳定状态类名和可见反馈：

- 默认。
- hover。
- focus。
- active / selected。
- disabled。
- loading / saving。
- pending。
- recorded / completed。
- warning。
- error。

状态反馈优先通过边框、背景、文字色、小 badge 和按钮状态表达，不通过新增装饰区块表达。

## 响应式策略

当前阶段以桌面端效率为主，同时维护明确断点：

- 1180px 至 1440px 使用紧凑桌面布局，保持八档数值单行和主操作可见。
- 1179px 以下切换为单列结构，取消左侧吸顶和视口内强制高度。
- 860px 以下继续收紧间距和组件布局。

移动端暂不作为主要重构目标，但必须满足：

- 无明显横向溢出。
- 无文本裁切。
- 无控件重叠。
- 主要操作仍可点击。
- 主流程纵向堆叠后仍能理解。

移动端精修应在桌面方案确认后单独规划。

## 实现边界

实现时必须沿用现有 Vue + CSS 架构。

- 不引入新 UI 框架。
- 不引入新的状态管理方案。
- 不修改 API 契约。
- 不重写业务逻辑。
- 不把 feature 样式塞回全局入口。
- 不做无关重构。
- 不为了视觉参考新增无业务意义的组件。

样式归属仍按 feature CSS 管理：

- 工作台主结构：`WuwaFrontend/src/styles/features/workspace.css`。
- 历史记录：`WuwaFrontend/src/styles/features/history.css`。
- 识别复核：`WuwaFrontend/src/styles/features/recognition.css`。
- 全局 shell 和 token：仅在确有跨页面价值时修改。

## 当前基线与后续维护

当前工作台已经完成圆角与边框 token、紧凑顶部导航、摘要指标、套装搜索、视口内配置区、档位保存状态、预测分组、浮动历史面板、暗色模式和响应式断点。后续改动应从明确问题出发，不重复把已完成内容写成待办路线。

纯视觉调整必须保持业务语义不变。若交互流程确实需要变化，应先形成专项设计，写清状态转换、边界和测试，再同步本文中的长期事实。

## 验收清单

一次合格的工作台 UI 修改至少需要满足：

- 没有恢复旧版 Activity Bar / Status Bar 方向。
- 保持当前圆角工作台基础，不做全局推倒重来。
- 视觉方向符合 V2.1：克制、圆角、浅色、工具型、高可读。
- 高频录入路径没有变长。
- 0/5 与已有录入项时的配置变化行为符合本文规则，且不会创建重复记录。
- 状态信息更容易扫读。
- 历史和识别复核没有喧宾夺主。
- 桌面端无明显拥挤、错位、裁切、重叠。
- 移动端无严重横向溢出。
- 改动范围聚焦于工作台及必要样式。
