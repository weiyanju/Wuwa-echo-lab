# 后台运行与性能规范

## 1. 文档定位

本文定义 `Wuwa` 本地助手长期后台运行与性能约束。

它不是某一次性能优化记录，而是以后开发窗口检测、截图、本地离线 OCR、识别流水线、诊断日志和设置项时都必须遵守的母规则。

本文主要回答：

- WPF 助手长期挂后台时应如何控制 CPU、内存和 I/O
- 什么情况下可以截图，什么情况下可以 OCR
- OCR 如何避免重复识别、阻塞 UI 或任务堆积
- 性能指标如何记录、展示和验收
- 哪些“优化”不能接受

如果某个实现方案与本文冲突，应先调整方案；如果确实需要例外，必须单独确认。

---

## 2. 核心结论

WPF 本地助手大部分时间是后台软件。

WPF 端核心性能目标固定为：

- 低延迟：用户触发识别、停止识别、切换页面、查看状态时应尽快得到反馈。
- 快速响应：OCR、截图、后端提交等长耗时任务不能阻塞窗口操作。
- 低内存占用：空闲态不加载重型资源，长时间运行不持续增长。
- 高效率：没有变化不重复截图和 OCR，相同截图必须复用缓存。
- 识别准确：不能为了快而牺牲字段准确度、数据归属和回滚可信度。

这些目标是 WPF 本地助手的核心规定，不是后期优化项。

因此它的性能目标不是“某一次 OCR 跑得最快”，而是：

- 长时间挂后台不明显占用用户电脑
- 用户需要识别时响应足够快
- 没有变化时不重复做重工作
- 出错、空闲、切换账号、关闭识别时能恢复到低占用状态
- 性能问题可以通过日志和指标定位

最重要的硬规则是：

**不允许持续全屏 OCR。**

同样重要的硬规则是：

**不允许用牺牲识别准确性换取表面速度。**

## 3. 后台运行状态机

后台识别必须按状态机运行，不能写成无边界循环。

推荐状态：

```text
Disabled
  -> Idle
  -> WindowSearching
  -> WindowFound
  -> CandidateDetecting
  -> Capturing
  -> HashChecking
  -> OcrQueued
  -> OcrRunning
  -> Parsed
  -> Submitting
  -> Cooldown
  -> Idle

ErrorRecoverable
  -> Idle

Stopping
  -> Disabled
```

状态含义：

- `Disabled`：用户未开启自动识别，不做窗口检测、不截图、不 OCR。
- `Idle`：后台空闲，只保留必要状态，不做重任务。
- `WindowSearching`：低频查找游戏窗口。
- `WindowFound`：已找到窗口，但还未判断是否需要截图。
- `CandidateDetecting`：用便宜方式判断是否可能进入识别场景。
- `Capturing`：截取必要区域。
- `HashChecking`：计算截图 hash，判断是否重复。
- `OcrQueued`：OCR 任务进入队列，等待唯一 worker 处理。
- `OcrRunning`：本地离线 OCR 正在运行。
- `Parsed`：OCR 文本已解析成结构化候选结果。
- `Submitting`：向后端提交结构化结果。
- `Cooldown`：短暂冷却，避免重复触发。
- `ErrorRecoverable`：可恢复错误，例如窗口丢失、截图失败、OCR 失败、后端暂不可达。
- `Stopping`：用户关闭后台识别，取消或收尾当前任务。

规则：

- 每个状态都必须可退出。
- UI 线程不能承载状态机循环。
- 后台状态变化应写入诊断日志。
- 用户必须能看到当前后台状态。
- 可恢复错误不能导致 UI 卡死或进程崩溃。

## 4. 分层触发策略

后台识别必须先做便宜判断，再做昂贵任务。

默认链路：

```text
是否开启自动识别
  -> 是否存在目标游戏窗口
  -> 窗口是否前台或可截图
  -> 是否处于可能变化的页面
  -> 局部截图
  -> hash / 像素变化判断
  -> OCR 缓存检查
  -> 本地离线 OCR
  -> parser / normalize
  -> 后端提交
```

允许的便宜判断：

- 进程或窗口标题检测
- 窗口句柄和尺寸检测
- 前台窗口检测
- 截图小区域 hash
- 像素变化检测
- 冷却时间判断
- 最近失败状态判断

不允许：

- 未找到游戏窗口时启动 OCR
- 未发生变化时重复 OCR
- 用 OCR 代替窗口检测
- 用全屏 OCR 判断是否需要识别
- 在 UI 页面事件里直接串联长耗时 OCR

---

## 5. 检测频率规则

检测频率必须和状态绑定，不能全程高频。

建议默认值：

| 场景 | 默认行为 |
| --- | --- |
| 自动识别关闭 | 不检测、不截图、不 OCR |
| 自动识别开启但未找到窗口 | 低频窗口检测，约 1-3 秒一次 |
| 找到窗口但未进入候选场景 | 低频或中低频检测 |
| 进入候选场景 | 短时间提高检测频率 |
| 截图 hash 无变化 | 回到低频或冷却 |
| OCR 失败 | 进入可恢复错误并退避 |
| 后端不可达 | 不丢结果，进入可恢复错误或待提交队列 |

规则：

- 高频检测必须有持续时间上限。
- 失败后必须退避，不能无限快速重试。
- 检测频率必须可配置，但默认值应保守。
- 配置项不能暴露成程序员式复杂参数，普通用户只需要“低占用/标准/快速”等模式。

---

## 6. 截图规则

截图是 OCR 前的必要步骤，但也必须控制成本。

规则：

- 默认只截取需要识别的局部区域。
- 不把完整截图作为常规后端上传内容。
- 截图后必须计算稳定 hash。
- 相同截图 hash 不应重复进入 OCR。
- 截图失败必须记录原因。
- DPI、分辨率、窗口缩放差异必须归入截图模块处理。

截图模块至少输出：

- 截图区域
- 截图时间
- 截图 hash
- 截图耗时
- 失败原因

---

## 7. OCR 队列规则

OCR 必须通过受控队列执行。

规则：

- 同一时间最多运行 1 个 OCR worker。
- 新任务进入前先检查缓存。
- 过期任务可以丢弃。
- 用户停止识别时，未开始任务必须取消。
- 正在运行的 OCR 如果引擎支持取消，应尽量取消；不支持时也不能阻塞 UI。
- OCR worker 不能直接更新复杂 UI 状态，只能产出事件或结果。

队列必须避免：

- 多个 OCR 并发抢 CPU
- 截图变化很快时任务越积越多
- 后台关闭后 OCR 仍继续写状态
- OCR 失败导致整个助手不可用

---

## 8. OCR 缓存规则

OCR 缓存是必需能力，不是可选优化。

至少需要两层缓存：

### 8.1 截图 hash 缓存

用途：

- 判断同一张截图是否已经处理过
- 避免重复 OCR
- 支持重复触发抑制

缓存 key：

```text
game_account_id + screenshot_region + screenshot_hash + ocr_provider_version
```

### 8.2 OCR 结果缓存

用途：

- 复用相同截图的 OCR 文本、字段、置信度和耗时
- 降低重复识别成本

缓存 value 至少包含：

- raw text
- normalized fields
- field confidence
- OCR elapsed ms
- parser version
- created time

规则：

- 缓存命中时不能再次调用 OCR 引擎。
- OCR provider 或 parser 版本变化时，旧缓存不能无条件复用。
- 缓存可以存本地，但重要业务结果仍必须通过后端持久化。
- 缓存清理策略必须存在，避免长期无限增长。

---

## 9. OCR 引擎加载规则

本地 OCR 引擎可能带来明显内存和启动成本，因此必须按需管理。

规则：

- 应用启动时不默认加载重型 OCR 引擎。
- 用户开启识别、手动识别或进入 OCR 页面时再加载。
- 加载状态必须可见，例如“OCR 初始化中”。
- 长时间空闲后可以释放重资源。
- 释放后再次识别允许有初始化成本，但不能让 UI 无响应。

引擎选择前必须确认：

- 离线可用性
- 安装体积
- 内存占用
- 单次 OCR 耗时
- 授权风险
- 中文/英文/数字识别效果
- 是否支持局部区域识别
- 是否支持取消或超时控制

---

## 10. 性能指标

性能不能靠感觉判断，必须有可观测指标。

至少记录：

- 当前后台状态
- 窗口检测耗时
- 截图耗时
- hash 计算耗时
- OCR 排队耗时
- OCR 运行耗时
- parser 耗时
- 后端提交耗时
- OCR 缓存命中率
- 截图 hash 重复抑制次数
- OCR 失败次数
- 后端提交失败次数
- 最近一次错误原因

UI 至少展示：

- 当前后台状态
- 最近一次识别耗时
- 最近一次 OCR 耗时
- 最近一次缓存是否命中
- 最近一次错误原因

诊断日志应包含更完整信息，方便后续定位性能瓶颈。

---

## 11. 准确性规则

OCR 识别必须同时追求速度和准确，不能只看耗时。

规则：

- 低置信度字段不能自动写入正式样本。
- 必填字段缺失时不能自动提交正式识别结果。
- raw OCR、normalized fields、field confidence 必须能追踪。
- 识别结果必须能进入复核、冲突、拒绝或回滚流程。
- 缓存命中不能跳过版本检查，OCR provider 或 parser 变化后不能无条件复用旧结果。
- 快速响应不能绕过 `GameAccount`、snapshot、duplicate hash 和回滚保护。

建议指标：

- 字段置信度
- 字段缺失率
- duplicate hash 命中率
- conflict/rejected 比例
- 人工复核后回滚比例
- parser 失败原因分布

如果一次优化让 OCR 更快，但明显增加误写、冲突或低置信度自动写入，这不是有效优化。

## 12. 阶段性性能目标

当前阶段先采用可验证的目标，不假装已经知道最终数字。

### 12.1 空闲态

空闲态指：

- 自动识别关闭；或
- 自动识别开启但没有目标游戏窗口；或
- 找到窗口但没有候选变化。

目标：

- 不触发 OCR。
- 不做全屏截图。
- CPU 占用应接近空闲。
- 内存不应持续增长。
- 日志不会高频刷屏。
- 不加载非必要重型 OCR 资源。

建议验收：

- 持续运行 10 分钟，观察 CPU、内存、日志增长。
- 未找到游戏窗口时，OCR 调用次数为 0。
- 自动识别关闭时，窗口检测和 OCR 调用次数为 0。

### 12.2 识别态

识别态指用户手动识别或后台检测到候选变化。

目标：

- 局部截图优先。
- 缓存命中时不调用 OCR。
- OCR 不阻塞 UI。
- 低置信度或字段缺失时不自动写入正式样本。
- 单次 OCR 耗时、总耗时和失败原因可见。
- 识别结果准确性、置信度和回滚路径可见。

建议验收：

- 相同截图重复触发时，第二次必须缓存命中。
- OCR 运行期间窗口仍可拖动、切换页面或停止识别。
- OCR 失败后可以再次识别，不需要重启软件。
- 低置信度或字段缺失样本进入 conflict/rejected/复核路径，而不是静默保存。

### 12.3 长时间运行态

长时间运行态指用户把助手挂在后台使用。

目标：

- 无明显内存泄漏。
- 错误可恢复。
- 任务不积压。
- 日志和缓存有清理策略。
- 后端不可达时不造成 UI 卡死。

建议验收：

- 长时间运行后后台状态仍可启动、停止、恢复。
- OCR 队列长度不会无限增长。
- 缓存文件或日志文件不会无限增长。

## 13. 性能验收门槛

涉及后台识别、截图、OCR、缓存、诊断的改动，默认需要回答：

- 自动识别关闭时是否完全不 OCR？
- 未找到游戏窗口时是否完全不 OCR？
- 相同截图是否命中缓存？
- OCR 是否在 UI 线程外运行？
- OCR worker 是否最多 1 个？
- OCR 失败是否可恢复？
- 后端不可达时是否可恢复？
- 是否记录 OCR 耗时？
- 是否记录缓存命中情况？
- 是否有测试覆盖 hash、cache key、重复抑制？
- 是否保证低置信度和字段缺失不会自动写入正式数据？
- 是否能追踪 raw、normalized、confidence 和 parser 版本？
- 是否证明 UI 仍能快速响应用户操作？

如果回答不清，这个改动不应视为完成。

---

## 14. 不允许的性能方向

以下方向默认不接受：

- 持续全屏 OCR。
- 多个 OCR worker 默认并发。
- OCR 任务无限排队。
- 为了省事取消 hash 或缓存。
- 为了追求低占用牺牲数据归属和识别正确性。
- 将完整截图常规上传给后端做 OCR。
- 把性能参数暴露成复杂开发者配置，让普通用户承担理解成本。
- 没有指标就宣称性能已优化。
- 为了低延迟绕过置信度、复核、幂等或回滚保护。
- 为了减少内存占用取消必要缓存、状态记录或诊断指标。

## 16. 给 Codex 与后续协作者的默认约束

- 写后台循环前先写状态机。
- 写真实 OCR 前先跑通 fake provider、hash、缓存和队列。
- 改 OCR 前先确认是否会影响安装体积、授权、内存或速度。
- 性能优化必须带测量点。
- 不能把“能识别”当成“能长期后台识别”。
- 不能把“识别很快”当成“识别可信”。
