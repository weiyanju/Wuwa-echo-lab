# 稳定期问题修复边界守则

## 1. 文档定位

本文定义 `Wuwa` 当前阶段的默认问题修复方式。

它不是长期架构文档的替代品，而是用来回答下面 4 个问题：

- 当前问题属于单点小修、边界判断，还是结构性执行单
- 这次修复的真实 owner 是谁
- 哪些修改是允许的，哪些会把边界重新弄脏
- 修完之后至少要验证到什么程度

如果某次局部实现习惯与 [`architecture.md`](./architecture.md) 冲突，以 `architecture.md` 为准。

## 3. 默认原则

### 3.1 先判断 owner，再判断怎么修

当前最常见的风险不是“大重构做坏”，而是“小修复慢慢把边界重新打散”。

默认顺序：

1. 先判断这个问题属于哪个 owner。
2. 再判断最小修复是否还能留在 owner 边界内。
3. 只有确认边界后，才进入实现。

### 3.2 小问题也不能按“哪里顺手改哪里”处理

以下做法默认都是越界信号：

- 为了修一个点，在 Vue `App.vue` 继续堆新业务
- 让页面绕过 API service 直接碰后端细节
- 让外部本地识别客户端直接写数据库

### 3.3 兼容壳可以存在，但必须变薄

允许少量兼容壳、转发层或历史适配层继续存在，但它们只能：

- 兼容旧调用
- 做转发
- 做类型适配
- 指向真实 owner

它们不能：

- 承接新业务主路径
- 承接新的平台实现
- 变成新的长期落点

## 4. 三种处理模式

### 4.1 小修执行模式

适用条件：

- owner 清晰
- 修复能留在同一层或同一模块内
- 不需要新增跨层抽象
- 不需要迁移职责

典型例子：

- 某个 API 错误提示文案不准确
- 某个前端格式化显示错误
- 某个测试断言需要跟随既有契约更新

要求：

- 只在真实 owner 内做最小修复
- 不顺手新增跨模块公共 helper
- 不让入口层继续变厚

### 4.2 边界判断模式

适用条件：

- 问题不大，但落点不完全清楚
- 有两个以上位置看起来都能改
- 写错层后续容易扩散

典型例子：

- 看起来是外部客户端 UI bug，但本质涉及 `GameAccount` 状态
- 看起来是 Web 显示问题，但本质是后端 API 字段含义不清
- 看起来是 OCR 失败，但本质是截图区域、缓存、parser 边界不清
- 看起来是“卡顿”，但本质是后台状态机、OCR 队列或缓存策略不清
- 看起来是接口小改，但本质会影响外部本地识别客户端、Web 和数据库契约
- 看起来是诊断增强，但本质会改变截图、日志或隐私边界

要求：

- 先明确推荐 owner
- 先明确允许修改的层
- 先明确禁止扩散的层
- 再降级为小修或升级为执行单

### 4.3 执行单模式

适用条件：

- 修复必然跨层
- 修复过程需要迁移职责
- 暴露的是结构性债务
- 如果不锁范围，实施过程会变成隐性大重构

典型例子：

- Vue `App.vue` 大规模拆分
- 后端 API 契约调整
- 本地后端迁移到云端服务

要求：

- 先写执行计划
- 锁目标、范围、非目标、阶段和验收
- 明确兼容策略和退出条件

## 5. 必须先停下来的信号

出现以下任一情况，不应继续按小修推进：

- 需要新增 shared/common，但说不清为什么是稳定共享能力
- 需要改后端 API 契约
- 需要改数据库结构
- 需要上传截图或改变 OCR 隐私边界
- 需要让外部本地识别客户端直接访问数据库
- 需要让 Vue `App.vue` 承接新的完整功能
- 实施者说不清“这段逻辑到底该归谁”

---

## 6. 高风险区

当前需要重点防止回流的区域：

- Vue `App.vue`
- 后端 `api/` 兼容层

这些区域可以改，但默认应先问：

- 它是不是在吸收本不属于它的逻辑？
- 有没有更真实的 owner？
- 这次是否应该先写执行单？

---

## 7. 默认验证门槛

小修默认：

- 跑命中的专项测试
- 或做能证明问题的最小验证

后端 API 或模型修改：

- 跑命中的 Django 测试
- 检查 migration 风险
- API 或 recognition 修复如果改变外部客户端契约，必须同步独立客户端仓库或保留兼容

Vue 工作流修改：

- 跑命中的前端测试
- 必要时运行 build

外部客户端的 OCR、截图和桌面 UI 修改由独立客户端仓库验证。

---

## 8. 验收时真正要看的事

稳定期验收不只看“功能有没有修好”，还要看：

1. 代码有没有留在真实 owner 内。
2. 有没有新增新的公共垃圾桶。
3. 有没有让入口层变厚。
4. 有没有让页面直接碰基础设施。
5. 有没有把结构性问题伪装成小修。

如果功能修好了，但边界明显变脏，就不应算合格修复。
