# 产品界面统一原则

> 前端 UI 方向以 [`web-ui-design-system-v2.md`](./web-ui-design-system-v2.md) 为最高优先级。本文档负责沉淀 `Wuwa` 三端共同产品气质、账号/UID 心智、数据可信与边界判断。

## 1. 文档定位

本文定义 `Wuwa` 所有用户界面共同遵守的长期原则。

它不替代 WPF 本地助手的具体 UI 规则，也不替代 Web 工作台的页面规范；它提供跨端一致的产品判断基线。

适用范围：

- WPF 本地助手。
- Vue Web 首页与工作台。
- 后续可能出现的云端管理页或轻量辅助页面。

## 2. 一句话原则

`Wuwa` 的界面应是：

> 清晰、克制、专业、低噪音的游戏数据工具。

用户应该感觉：

- 当前账号和 UID 很明确。
- 数据状态可信。
- 识别过程可理解。
- 错误可以处理。
- 日常使用不被打扰。
- 深度分析时信息密度足够。

用户不应该感觉：

- 像营销页。
- 像大型企业后台。
- 像调试工具。
- 像视觉特效展示。
- 像需要学习大量参数才能使用的软件。

## 3. 三端角色

### 3.1 WPF 本地助手

WPF 是日常助手入口。

它应该：

- 小窗口优先。
- 后台友好。
- 状态清楚。
- 操作少而准。
- 聚焦截图、OCR、识别、日志和设置。

它不应该：

- 承接复杂数据管理。
- 做成全屏工作台。
- 暴露后端地址等开发者信息。

具体规则见 [`wpf-assistant-ui-guidelines.md`](./wpf-assistant-ui-guidelines.md)。

### 3.2 Web 首页

Web 首页是产品入口和登录入口。

它应该：

- 保留 `Wuwa Echo Terminal / 鸣潮声骸终端` 的终端感。
- 建立产品可信度。
- 提供清晰的登录 / 注册入口。
- 引导登录后的 UID 绑定。

它不应该：

- 提前暴露登录后的工作台内部导航。
- 展示假声骸数据。
- 做成泛 SaaS 营销页。
- 把登录后工作台的布局复杂度带到首页。

具体规则见 [`web-homepage-terminal-design.md`](./web-homepage-terminal-design.md)。

### 3.3 Web 工作台

Web 是深度工作台。

它应该：

- 承载声骸数据管理。
- 承载统计、预测、评估。
- 支持筛选、表格、图表和详情页。
- 信息密度高但结构清晰。
- 适合用户主动打开后深入查看。

它不应该：

- 复制 WPF 的后台识别职责。
- 为了视觉展示牺牲数据可读性。
- 创造另一套账号或 UID 心智。
- 变成 VS Code 客户端式完整 IDE Shell。
- 为了参考外部产品而新增无业务意义的栏位。

具体规则见 [`web-workbench-ui-guidelines.md`](./web-workbench-ui-guidelines.md)。

### 3.4 后端相关界面

如果未来出现管理页或诊断页，应遵守：

- 只展示用户需要理解的信息。
- 不把内部技术细节暴露给普通用户。
- 隐私、数据归属、错误恢复优先于好看。

## 4. 信息层级

所有界面默认按以下优先级展示信息：

1. 当前系统账号。
2. 当前游戏 UID / `GameAccount`。
3. 当前数据或识别状态。
4. 当前可执行动作。
5. 最近结果或错误。
6. 诊断和高级设置。

规则：

- 账号和 UID 状态不能藏得太深。
- 错误信息必须说明用户能做什么。
- 成功、警告、错误不能只靠颜色区分。
- 低频设置不能抢主路径视觉权重。

## 5. 视觉语言

### 5.1 外部参考的使用方式

允许在设计讨论和阶段性文档中明确引用外部产品作为参考，例如 VS Code 官网、Linear 和 Vercel。

但引用方式必须符合：

- 外部产品只能作为视觉词汇，不作为页面骨架。
- 必须落回 `Wuwa` 自己的业务场景和数据流程。
- 不能为了“像某个产品”添加无业务意义的界面 chrome。
- 长期规则应描述为 `Wuwa` 自己的可执行规范。

### 5.2 色彩

颜色应服务语义：

- 主色：关键动作、当前选中、重要状态。
- 成功色：保存、提交、识别成功。
- 警告色：低置信度、需要用户确认。
- 错误色：失败、不可提交、权限或连接问题。
- 中性色：背景、边框、辅助文本、分隔。

规则：

- 不使用单页临时配色体系。
- 不让整个产品被单一色相支配。
- 状态色不能只作为装饰。
- Web 当前以浅色、蓝色强调、低噪音工具感为主。

### 5.3 字体与字号

规则：

- 标题只用于当前区域的真实层级。
- 表单、表格、状态文案优先保证可读性。
- 小窗口内不使用夸张大标题。
- 不用负字距。
- 不用随视口宽度缩放字号。
- 等宽字体只作为 UID、协议标签、状态码、短 metadata 的点缀。

### 5.4 圆角、边框和阴影

圆角是当前 Web 视觉升级的重要抓手，但必须有节制。

规则：

- 圆角收敛到少数档位。
- 卡片、输入框、按钮的圆角应统一。
- Web 工作台可采用现代圆角工具型风格。
- WPF 小窗口仍以紧凑、清晰为优先。
- 阴影只用于浮层或真正需要层级的元素。
- 不用重阴影制造“高级感”。
- 不强行回到旧 V2.0 的极小圆角 IDE 风。

### 5.5 间距和密度

规则：

- WPF 偏紧凑。
- Web 可以更高信息密度。
- 操作区和内容区要有明确分隔。
- 密集数据区域优先使用表格、分组和筛选，而不是装饰卡片堆叠。
- 首页可以比工作台更有氛围；工作台应比首页更重效率。

## 6. 组件原则

组件和样式必须优先复用。

规则：

- 相同语义的按钮、输入框、状态标签、空状态、错误提示应使用同一套组件或样式。
- 新增 UI 前先查现有组件、样式、token。
- 只有出现新的长期语义时，才允许扩展组件或 token。
- 不允许多个页面为相同效果各写一套局部实现。
- 局部一次性样式不能沉淀成长期事实。

### 6.1 按钮

按钮层级：

- 主按钮：当前页面最重要动作。
- 次按钮：辅助动作。
- 谨慎按钮：回滚、撤销、删除等。
- 图标按钮：工具型动作。

规则：

- 一个局部区域不要出现多个同强度主按钮。
- destructive 动作必须有明确语义。
- 禁用状态必须说明原因或能通过上下文理解。

### 6.2 表单

规则：

- 普通用户不需要看到后端地址。
- 表单错误应贴近对应输入。
- 长表单应分组，不应一次铺满。
- 登录、注册、UID 初始化要保持短路径。

### 6.3 状态

每个重要流程至少有这些状态：

- idle。
- loading。
- success。
- warning。
- error。
- disabled。

识别和 OCR 相关流程还应有：

- waiting。
- queued。
- running。
- cached。
- low confidence。
- recoverable error。

### 6.4 数据展示

规则：

- Web 数据管理优先使用表格、筛选、排序、详情。
- WPF 只展示最近结果和关键状态，不承载完整数据表。
- 图表必须服务判断，不做装饰。
- 概率、置信度、数量和 UID 等关键值应格式稳定。

## 7. 文案原则

文案面向用户，不面向开发者。

规则：

- 不显示“后端地址”这类开发者概念。
- 错误文案应说明用户下一步能做什么。
- 状态文案要短。
- 技术细节放诊断日志，不放主界面。

示例方向：

- 使用：“无法连接服务，请确认本地服务已启动。”
- 避免：“HTTP request failed。”
- 使用：“未检测到游戏窗口。”
- 避免：“window handle is null。”

## 8. 响应式与窗口适配

WPF 和 Web 都必须考虑不同尺寸。

规则：

- WPF 首先保证小窗口可用。
- Web 首先保证桌面数据工作台可用，同时移动端不崩。
- 当前工作台重构阶段可以先聚焦桌面，但不能产生严重横向溢出、文字裁切或控件重叠。
- 文本不能溢出按钮、卡片、状态标签。
- 关键操作不能因为窗口缩小而不可访问。
- 滚动区域要清楚，不要让用户分不清页面和面板谁在滚动。

## 9. 可访问性与可理解性

规则：

- 不只靠颜色表达状态。
- 点击目标不能过小。
- hover、focus、disabled 状态要完整。
- 重要操作需要明确反馈。
- 加载时间超过短暂瞬间时要显示状态。

## 11. 给 Codex 与后续协作者的默认约束

- 不把“看起来像某个产品”当作最终设计依据。
- 可以引用外部产品作为阶段性审美参照，但最终必须写成 `Wuwa` 自己的规则。
- 不再按旧 V2.0 的完整 IDE 化方向推进 Web 工作台。
- WPF 和 Web 可以有不同密度，但必须保持同一产品气质。
- UI 改动不能脱离账号、UID、数据可信、后台低打扰这些核心产品约束。
