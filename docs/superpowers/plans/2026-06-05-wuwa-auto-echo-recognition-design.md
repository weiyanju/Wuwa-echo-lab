# 鸣潮声骸自动识别与后台采集设计

## 目标

为现有鸣潮声骸记录与预测系统增加一个 Windows 本地助手，使用户在游戏内连续强化声骸时不需要频繁切换网页。助手在后台检测“强化成功”提示，等待用户回到声骸详情页后识别完整声骸状态，自动补录可信数据，并将异常数据隔离到事后复盘区。

第一版的产品目标是“游戏内零打断采集”：

- 用户可以一直留在游戏中开词条。
- 系统自动记录高置信、合法、可匹配的强化结果。
- 网页主要用于强化结束后的统计、预测和异常复盘。
- 识别异常不能污染正式统计和预测样本。

## 当前系统上下文

仓库当前包含：

- `Wuwa`：Django 后端，已有用户、声骸记录、声骸副词条、预测、统计和模型评估 API。
- `WuwaFrontend`：Vue + Vite 前端，已有工作台、历史声骸、预测面板、统计页和模型评估页。
- `EchoRecord`：正式声骸记录，包含用户、声骸 ID、COST、套装、主词条、状态等字段。
- `SubstatRoll`：正式副词条记录，包含 position、substat_type、tier_value、enhance_phase 和 tuning_order。
- `TIER_TABLES`：后端已有副词条合法档位与概率表，可用于 OCR 数值校正。

现有第一版明确未包含 OCR 或截图识别。本设计是在现有系统上扩展，不重建 Web 应用。

## 产品原则

### 完整状态优先

“强化成功”弹窗只作为触发信号和增量参考，不能作为唯一入库依据。每次强化成功后，助手必须等待用户点击返回声骸详情页，再识别详情页中的完整声骸信息：

- 声骸名称
- 套装
- COST
- 等级
- 主词条
- 全部已出现副词条
- 每个副词条的档位数值

正式补录以完整详情页快照为准。

### 不打断游戏流程

用户不需要在每次强化后打开网页确认。正常结果自动入库，异常结果进入事后复盘。游戏内只显示轻量反馈，例如“已记录 2 条”“识别异常 1 条”“当前 4/5”。

### 数据质量优先

系统必须区分原始识别日志和正式统计样本。OCR 原文、截图哈希、字段置信度和匹配方式会被保存；只有合法且可匹配的结果才进入 `EchoRecord` / `SubstatRoll`，参与预测和统计。

### 不侵入游戏进程

本地助手只做窗口检测、屏幕捕获、模板匹配和 OCR，不读取游戏内存，不注入进程，不修改游戏文件。

## 总体架构

```text
Windows 本地助手
  -> 检测鸣潮窗口
  -> 低频监测“强化成功”
  -> 捕获强化弹窗和详情页截图
  -> OCR 与字段校正
  -> 调用后端识别 API
  -> 显示本地轻反馈/悬浮窗

Django 后端
  -> 接收识别会话和识别快照
  -> 保存原始识别日志
  -> 标准化字段
  -> 匹配或创建声骸记录
  -> 自动补录缺失副词条
  -> 隔离异常结果
  -> 刷新预测与统计数据

Vue 前端
  -> 显示正式工作台、历史、统计、预测
  -> 显示自动采集会话摘要
  -> 显示异常复盘列表
```

## 本地助手职责

本地助手应是托盘常驻桌面程序，而不是 Windows Service。原因是桌面程序可以访问当前用户会话的游戏窗口、注册快捷键、显示置顶悬浮提示；Windows Service 通常不适合访问交互式桌面。

第一版助手职责：

- 启动后驻留托盘。
- 自动或手动选择鸣潮窗口。
- 以低频方式检测“强化成功”提示。
- 检测成功后记录弹窗区域截图和本次新增副词条文本。
- 等待详情页重新出现。
- 识别详情页完整声骸状态。
- 将识别快照发送到 Django 后端。
- 显示轻量结果提示。
- 提供手动重新识别和撤销最近一次采集的快捷键。

建议快捷键：

- `Ctrl+Alt+R`：重新识别当前详情页。
- `Ctrl+Alt+U`：撤销最近一次自动入库。
- `Ctrl+Alt+H`：隐藏或显示悬浮提示。

## 强化成功检测

游戏流程：

1. 用户点击强化按钮。
2. 材料充足时，游戏显示“强化成功”。
3. “强化成功”下方显示本次强化新开的副词条，可能是 1 到 5 条。
4. 用户再次点击后回到声骸详情页。
5. 详情页显示声骸名称、套装、主词条和所有副词条。

助手平时不做全屏 OCR。推荐流程：

```text
Idle
-> 低频捕获游戏窗口局部区域
-> 模板匹配“强化成功”
-> 命中后必要时 OCR 二次确认
-> 捕获强化成功弹窗下方新增词条区域
-> 等待详情页出现
-> 识别完整详情页快照
```

检测策略：

- 优先使用模板匹配识别“强化成功”UI。
- 模板匹配分数接近阈值时，再用 OCR 确认文字。
- 使用截图哈希和冷却时间避免同一次强化成功重复触发。
- 触发后延迟约 300 到 800ms 等待弹窗动画稳定。
- 回详情页后再延迟约 300 到 800ms 等待详情页文本稳定。

## OCR 与字段校正

OCR 不应直接决定最终字段。识别结果必须经过标准字典和合法档位校正。

字段来源：

- 声骸名称：来自声骸名称字典。
- 套装：来自 `sonataEffects` 或后端套装字典。
- COST：来自详情页 COST 显示或声骸基础信息。
- 主词条：来自 `MAIN_STATS_BY_COST` 校验。
- 副词条类型：来自 `SUBSTAT_TYPES` 和中文标签字典。
- 副词条数值：来自 `TIER_TABLES` 合法档位表。

校正规则：

- 文本字段使用相似度匹配到标准名称。
- 副词条数值只允许落到该词条的合法档位。
- 如果 OCR 数值接近多个合法档位，标记为低置信。
- 如果主词条不属于该 COST 的合法主词条，识别快照进入异常。
- 如果同一声骸快照中出现重复副词条，识别快照进入异常。

## 声骸身份匹配

声骸没有稳定唯一标识，所以匹配依赖完整状态指纹。

声骸基础指纹：

```text
名称 + 套装 + COST + 主词条
```

副词条序列指纹：

```text
position 1: 副词条类型 + 档位数值
position 2: 副词条类型 + 档位数值
...
```

完整匹配指纹：

```text
名称 + 套装 + COST + 主词条 + 已出现副词条序列
```

等级可作为辅助字段，但不能作为唯一依据，因为调谐进度与等级绑定，且用户可能跨声骸、跨时间继续强化。

### 匹配规则

识别到详情页完整快照后：

1. 找出同一用户下基础指纹相同且未归档的候选声骸。
2. 优先寻找“数据库中已有副词条序列是当前快照副词条序列前缀”的候选。
3. 如果只有一个前缀候选，判定为同一个声骸继续强化。
4. 如果没有前缀候选，且当前快照合法，则创建新声骸。
5. 如果多个候选前缀完全相同，按时间顺序选择最近强化或最早待补全的候选。
6. 如果候选与快照存在副词条冲突，进入异常，不写正式样本。

示例：

```text
数据库已有声骸 A：
暴击率 6.3，攻击百分比 7.9

详情页快照：
暴击率 6.3，攻击百分比 7.9，暴击伤害 15.0，生命百分比 10.1

结果：
匹配声骸 A，自动补录 position 3 和 position 4。
```

如果两个声骸名称、套装、主词条和第一条副词条类型相同，但数值不同，例如一个是暴击率 6.3，另一个是暴击率 10.5，则副词条档位数值用于区分两个声骸。

如果两个声骸连基础指纹和已有副词条档位序列都相同，则按时间顺序兜底，并在识别日志中标记匹配方式为 `time_order`。

### 匹配状态

- `exact`：基础指纹一致，已有副词条序列是当前快照的完整前缀，档位完全匹配。
- `probable`：基础指纹一致，新增数量与强化弹窗一致，但存在非关键低置信字段。
- `time_order`：多个候选无法通过指纹区分，按时间顺序匹配。
- `created`：没有候选，创建新声骸。
- `conflict`：存在冲突或无法安全判断，不进入正式统计。

自动入库允许状态：

- `exact`
- `probable`
- `time_order`
- `created`

其中 `probable` 和 `time_order` 必须保留识别日志和复盘标记，方便事后检查。

## 数据流

```text
1. 用户在游戏中点击强化。
2. 本地助手检测到“强化成功”。
3. 本地助手识别弹窗下方本次新增副词条，保存 delta。
4. 用户点击返回声骸详情页。
5. 本地助手识别详情页完整 snapshot。
6. 本地助手提交 delta + snapshot + 截图哈希 + 置信度到后端。
7. 后端保存 RecognitionSession 和 RecognitionSnapshot。
8. 后端标准化字段并执行声骸匹配。
9. 后端自动创建或更新 EchoRecord。
10. 后端只补录数据库中缺失的 SubstatRoll。
11. 后端返回本次处理结果。
12. 本地助手显示轻量提示。
13. 用户之后打开网页查看统计、预测和异常复盘。
```

## 后端数据模型扩展

建议新增识别日志模型，不直接把 OCR 结果写进正式表。

### RecognitionSession

表示一次本地助手采集会话。

字段：

- `user`
- `client_id`
- `started_at`
- `ended_at`
- `game_window_title`
- `screen_resolution`
- `status`
- `created_count`
- `updated_count`
- `conflict_count`

### RecognitionSnapshot

表示一次强化成功后的完整识别快照。

字段：

- `session`
- `trigger_type`：`enhance_success` 或 `manual_rescan`
- `popup_delta_raw`
- `detail_snapshot_raw`
- `normalized_snapshot`
- `field_confidence`
- `screenshot_hash`
- `popup_screenshot_hash`
- `detail_screenshot_hash`
- `match_status`
- `matched_echo`
- `created_echo`
- `created_roll_count`
- `warnings`
- `status`：`saved`、`ignored_duplicate`、`conflict`、`rejected`
- `created_at`

截图文件本身第一版可以不入库，只保存哈希与可选本地路径。若后续需要网页复盘截图，再增加受控的截图上传和清理策略。

### EchoRecord 扩展建议

可新增辅助字段：

- `recognition_fingerprint`
- `recognition_match_quality`
- `last_recognized_at`
- `auto_imported`

这些字段不是一期必须，但有助于后续复盘和匹配调试。

## API 设计

新增接口建议：

- `POST /api/recognition/sessions/`
  - 创建本地助手采集会话。

- `POST /api/recognition/snapshots/`
  - 提交一次强化成功后的弹窗 delta 和详情页 snapshot。
  - 后端完成标准化、匹配和自动补录。

- `GET /api/recognition/sessions/{id}/`
  - 查看本次采集会话摘要。

- `GET /api/recognition/conflicts/`
  - 查看异常识别结果。

- `POST /api/recognition/snapshots/{id}/reject/`
  - 用户在网页事后拒绝某条异常识别。

- `POST /api/recognition/snapshots/{id}/apply/`
  - 用户事后修正并应用某条异常识别。

第一版可以只实现创建会话、提交快照和查看异常列表，其余接口随复盘能力扩展。

## 前端产品设计

网页不做逐条确认，而是做事后复盘。

新增“自动采集”区域：

- 当前或最近一次本地助手会话。
- 本次识别次数。
- 自动入库副词条数量。
- 创建声骸数量。
- 更新声骸数量。
- 异常数量。
- 最近一次识别状态。

新增“异常复盘”列表：

- 基础信息识别失败。
- 副词条数值不合法。
- COST 与主词条不匹配。
- 多个候选无法区分。
- 识别快照和数据库已有记录冲突。
- OCR 低置信字段。

异常记录默认不参与统计和预测。用户可以事后修正并应用，或丢弃。

## 本地反馈与悬浮窗路线

### 一期轻反馈

一期只需要轻量提示，不需要完整预测悬浮窗。

提示内容：

- 已记录 N 条。
- 当前声骸已识别 X/5 条。
- 识别异常 N 条。
- 最近一次匹配状态：精确、按时间顺序、新建、异常。

### 后续悬浮预测窗

采集链路稳定后，再实现完整置顶悬浮窗：

- 当前声骸基础信息。
- 已开副词条。
- 下一条 Top 3 预测。
- 样本阶段和置信度提示。
- 最近一次识别状态。
- 异常数量。
- 快捷键提示可隐藏，默认不打断用户。

悬浮窗由本地助手实现，网页继续作为主工作台和统计后台。

## 错误处理

### 重复触发

同一次强化成功可能被检测多次。系统使用以下信息去重：

- 强化成功弹窗截图哈希。
- 详情页截图哈希。
- 时间窗口冷却。
- 同一声骸同一副词条序列已保存检查。

重复结果标记为 `ignored_duplicate`，不写正式样本。

### OCR 低置信

低置信字段处理：

- 可由字典和合法档位唯一校正的字段继续处理。
- 无法唯一校正的字段进入异常。
- 低置信但已自动入库的 `probable` 和 `time_order` 记录必须保留复盘标记。

### 漏检

如果漏掉一次强化成功，用户可以通过快捷键重新识别当前详情页。因为系统识别的是完整副词条列表，只要当前详情页包含全部已开词条，就可以通过前缀匹配补录缺失位置。

### 顺序交错

用户可以先开声骸 A 的 2 条，再开声骸 B 的 1 条，再回到声骸 A 继续开。系统不依赖“上一次强化的是同一个声骸”，而是每次按详情页完整快照重新匹配声骸。

## 阶段计划

### 阶段一：后台自动采集 MVP

范围：

- Windows 本地助手托盘常驻。
- 鸣潮窗口检测。
- “强化成功”模板检测。
- 回详情页后完整 OCR。
- 字段标准化和合法档位校正。
- 后端识别会话和快照日志。
- 声骸指纹匹配。
- 高置信自动创建或更新正式记录。
- 异常隔离。
- 本地轻提示。
- 手动重新识别和撤销最近一次记录。

不包含：

- 完整置顶预测悬浮窗。
- 全自动处理异常。
- 云端同步截图。
- 多语言 OCR。
- 独占全屏强适配。

### 阶段二：网页事后复盘

范围：

- 自动采集会话摘要。
- 异常识别列表。
- 异常修正后应用。
- 异常丢弃。
- 按匹配状态查看自动入库记录。
- 对 `probable` 和 `time_order` 记录做筛选。

### 阶段三：游戏内悬浮预测窗

范围：

- 置顶半透明悬浮窗。
- 当前声骸信息。
- 已开副词条。
- 下一条 Top 3 预测。
- 识别状态和异常计数。
- 快捷键隐藏、显示、重新识别、撤销。

### 阶段四：高置信自动化优化

范围：

- 根据历史识别样本调整置信阈值。
- 优化模板匹配和分辨率适配。
- 增加校准工具。
- 改进同指纹声骸的时间顺序匹配策略。
- 支持更多游戏分辨率和 UI 缩放比例。

## 测试策略

### 后端测试

- 详情页快照可以创建新声骸。
- 详情页快照可以匹配已有声骸并补录缺失副词条。
- 已有副词条序列必须是当前快照前缀才允许自动补录。
- 副词条档位不合法时进入异常。
- COST 与主词条不匹配时进入异常。
- 同一声骸重复副词条时进入异常。
- 多个候选完全相同时使用时间顺序匹配并标记。
- 重复截图哈希不会重复入库。
- 异常识别不参与统计和预测。

### 本地助手测试

- 能检测鸣潮窗口。
- 能在常见分辨率下检测“强化成功”。
- 同一次强化成功不会重复触发。
- 能等待详情页出现后再 OCR。
- 快捷键重新识别可补录漏检结果。
- 悬浮轻提示不会阻塞游戏操作。

### 端到端场景

- 连续强化同一个声骸 1 到 5 条。
- 声骸 A 开 2 条，声骸 B 开 1 条，再回声骸 A 开 2 条。
- 两个同名同套装同主词条声骸，第一条副词条类型相同但档位不同。
- 两个声骸基础指纹和副词条序列完全相同，按时间顺序匹配。
- OCR 把数值识别到非法档位，进入异常。
- 用户强化结束后打开网页查看会话摘要和异常列表。

## 部署与运行

开发环境：

- Django 后端继续运行在 `127.0.0.1:8000`。
- Vue 前端继续运行在 `127.0.0.1:5173`。
- Windows 本地助手通过本地 HTTP API 与 Django 通信。

运行建议：

- 推荐游戏使用窗口化或无边框窗口化。
- 独占全屏下，截图捕获和悬浮窗可能不稳定。
- 本地助手应明确显示当前连接的用户和后端地址，避免写入错误账户。

## 安全与隐私

- 助手只捕获鸣潮窗口相关画面。
- 默认不上传完整截图，只上传识别字段和截图哈希。
- 若后续启用截图复盘，需提供本地清理策略和用户可见开关。
- 本地助手不读取游戏内存，不注入进程。
- 后端所有识别数据必须按用户隔离。

## 成功标准

阶段一完成后，应满足：

- 用户连续强化时无需切换网页。
- 检测到“强化成功”后，系统能在回详情页后自动识别完整声骸状态。
- 已有声骸可通过副词条档位序列继续匹配。
- 跨声骸、跨顺序强化不会依赖上一次操作上下文而误录。
- 高置信合法结果自动进入正式样本。
- 异常结果不影响统计和预测。
- 用户事后能在网页看到本次自动采集摘要。

## 待实施前确认

实施前需要确认具体本地助手技术栈。推荐优先评估 .NET WPF / WinUI，因为它更适合 Windows 托盘、快捷键、窗口捕获和置顶悬浮窗。OCR 引擎可先以 PaddleOCR 或 Windows OCR 做原型，再根据识别准确率决定是否训练或微调专用识别流程。
