# Wuwa 设计治理与 Impeccable 审查边界设计

## 背景

`DESIGN.md` 是 Wuwa Web 视觉 token、字体、组件语言和交互状态的最高设计入口。当前文档同时混入了项目已经批准的视觉事实与 Impeccable 生成的通用目标规则，导致后续 audit 建议可能被误解为全局改造授权。此前批量落实 audit 时已经出现配色漂移、浅色模式文字过灰和功能图形被误判为装饰等回归。

Impeccable 的 `audit` 本质是技术诊断和候选问题清单，不是设计定稿，也不直接授权修改颜色、字体、圆角、阴影或组件结构。

## 目标

- 明确当前已经批准的项目视觉是后续演进的默认基线。
- 保留 Impeccable 对交互、语义、性能、响应式和可读性问题的诊断价值。
- 阻止 audit 分数、通用硬规则或颜色字面量计数直接触发全局视觉改造。
- 要求 token 整理、主题收敛和代码重构默认保持零视觉变化。
- 让 `DESIGN.md` 与 `.impeccable/design.json` 表达同一套治理规则。

## 方案比较

### 方案 A：继续以 Audit 规则驱动全局修复

优点是执行快速、指标容易提高。缺点是通用检查会覆盖 Wuwa 已形成的视觉语言，无法区分功能图形、数据可视化颜色和装饰性样式，已经被实际回归证明风险过高，因此不采用。

### 方案 B：完全冻结当前界面并忽略 Audit

优点是不会产生视觉漂移。缺点是会放弃登录内容可见性、重复交互语义、真实横向溢出等有价值的问题发现，也无法逐步提高设计一致性，因此不采用。

### 方案 C：批准基线 + 分级审查 + 零漂移实施

将当前已批准的渲染结果作为默认基线，把 audit 发现分为无视觉修复、需要实测、需要设计批准和明确例外四类。只有用户批准的视觉提案才能改变基线；token 和工程整理先以完全保留最终色值与排版为目标。该方案兼顾设计稳定性与长期质量，作为本次选定方案。

## 设计治理规则

### 1. 已批准基线优先

当前已经被用户确认的页面截图、浏览器渲染结果、稳定实现和明确设计决策共同构成批准基线。`DESIGN.md` 负责总结这一基线并指导渐进演进，不允许通用工具规则自动覆盖它。

当 `DESIGN.md`、`.impeccable/design.json` 与实现存在冲突时：

1. 不自动修改代码迎合文档。
2. 不自动降低文档迎合代码。
3. 将冲突标记为待决策项。
4. 在用户批准具体方案后同步文档、实现和测试。

### 2. Audit 只产生候选问题

Audit 的严重等级、健康分数、命令建议和字面量数量都不构成修改授权。每项发现必须先归类：

- **无视觉修复**：语义 HTML、ARIA 关联、焦点管理、内容默认可见等；可在保持截图稳定的前提下实施。
- **实测后决定**：动画性能、CSS 加载、字体请求、响应式溢出和点击目标；必须先获得浏览器或性能数据。
- **视觉提案**：配色、字体层级、圆角、阴影、按钮造型和动效语言；必须提供局部前后对比并获得用户批准。
- **项目例外**：真实表达路径、进度、数据结构或品牌交互的功能图形；记录后不再按装饰性反模式反复整改。

### 3. 零视觉漂移

颜色 token 化、CSS ownership 整理、主题变量收敛和重复样式抽取的第一阶段只能改变命名与引用方式，不能改变最终计算颜色、字体角色、字号、字重、间距或组件几何。

任何视觉变化必须：

- 限定到一个页面或组件族。
- 说明解决的具体用户问题。
- 提供浅色模式前后截图；涉及主题时同时提供暗色截图。
- 检查桌面基准与相关窄屏断点。
- 避免全局搜索替换配色或文字 token。

### 4. 可读性是防回归底线，不是调色目标

关键正文、表单值、操作标签、错误信息和焦点状态必须清楚可读。对比度检查用于发现文字过灰、状态不可辨和 placeholder 不可读等真实回归，不用于按分数批量重映射项目色板。

禁用内容、装饰线、非文字图形和低权重图表刻度应按其真实语义判断，不强制与正文使用同一视觉权重。任何为了改善对比指标而进行的颜色调整仍属于视觉提案，必须获得批准。

### 5. 设计 token 分层

- **全局语义 token**：主色、文字、表面、边框、成功、警告和错误。
- **Feature token**：评估模型、Bayes 路径、覆盖范围、识别与工作台专属语义。
- **局部可视化颜色**：允许在数据图形内部保留字面量，但必须表达具体数据含义并提供需要的主题映射。

颜色字面量数量不等于设计缺陷数量。不得把评估页所有图表颜色加入全局调色板，也不得为了减少统计数字而改变现有视觉。

### 6. 明确例外

以下现有元素属于已经批准的功能或品牌图形，不按装饰性侧边条处理：

- Bayes Exact / Wildcard 路径左侧的实线与虚线路径标记。
- 登录标题的 4px 打字光标及其已批准间距。
- 真实表达进度、概率分布、模型路径或状态结构的图形线条。

例外只保护其功能语义，不豁免溢出、遮挡、错误交互或不可读文字等真实缺陷。

## 文档同步

- `DESIGN.md` 增加“使用方式与审查边界”，替换将 Impeccable 硬标准置于项目基线之上的规则。
- `.impeccable/design.json` 的 `narrative.overview`、`rules`、`dos` 与 `donts` 同步同义约束。
- 保持现有颜色、字体、圆角、间距和组件结构化值不变；未决的文档与实现差异留待后续逐组件审查。
- 本次不修改 Vue、CSS、图片、字体资源或运行时行为。

## 验收标准

- 两份设计入口都明确 audit 只产生候选问题，不能自动触发视觉改造。
- 两份设计入口都明确当前批准基线和零视觉漂移原则。
- 两份设计入口都保留 Bayes 路径与登录打字光标例外。
- 可读性规则不再把 audit 分数当作配色目标，同时仍禁止关键文字变成不可读灰色。
- `.impeccable/design.json` 能被标准 JSON 解析器读取。
- `git diff` 不包含任何前端实现文件或现有色值变更。

## 后续但不属于本次范围

- 登录页动画兜底、登录错误关联和评估页嵌套交互的无视觉修复。
- 按实际最终值提取全局与 feature token。
- 按组件族审查按钮、圆角、阴影和 hover 语言。
- 基于真实网络与性能数据优化 CSS 和字体加载。
